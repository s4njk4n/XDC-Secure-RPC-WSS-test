Private RPC and WSS for your XDC node

Run an XDC node with HTTPS and WebSocket endpoints that only the IP addresses you choose can use. One command installs it; after that, a menu looks after your allowlist, SSH safety, encrypted backups and updates. For any node operator, including Plugin RPCaaS operators.

  • Self-hosted
  • Free and open source
  • Mainnet and Apothem
  • Ubuntu 24.04 and 26.04

1

Get a server

Any VPS provider works.

  • Ubuntu 24.04 or 26.04 LTS, with root or sudo access.
  • For a full node: 6+ CPU cores, 16 GB RAM or more (32 GB for a busy endpoint), a 2 TB+ SSD. 1.5 TB is enough if you sync from scratch instead of using a snapshot. An archive node needs several times more disk.
2

Point a domain at it

Your endpoints use it, and the certificate is issued for it.

  • At your DNS provider, create an A record for a name such as rpc.example.com, pointing to the server’s IP address.
  • Don’t add an AAAA (IPv6) record: the endpoints work over IPv4.
  • If your DNS is at Cloudflare, set the record to DNS only (grey cloud).
3

Open the ports

Only needed if your VPS provider has a firewall in its control panel. The server’s own firewall is set up for you.

PortWhy
443 TCPYour RPC and WSS endpoints.
80 TCPCertificate renewals. The server keeps it closed except while a renewal runs.
30303 TCP and UDPP2P: other XDC nodes connect here. Apothem uses 30312. You can choose another port during setup.
Your SSH portUsually 22. If you move SSH to another port during setup, allow that one first.
4

Run the installer

Log in to the server with SSH, paste this line and press Enter.

curl -fsSL --remote-name-all https://github.com/s4njk4n/XDC-Secure-RPC-WSS-test/releases/latest/download/xdc-rpc.sh{,.sha256} && sha256sum -c xdc-rpc.sh.sha256 && sudo bash xdc-rpc.sh

It downloads the latest release, checks it against its published checksum, installs the xdc-rpc command and starts setup. Afterwards, sudo xdc-rpc opens the menu.

5

Answer the questions

Nothing on the server changes until you confirm the summary at the end. Use the keyboard: ↑↓ to choose (or to scroll a long page), Enter to press the highlighted button, Tab or ←→ to pick another button, Esc to go back.

  1. Network and node type: Mainnet or Apothem; full (recommended) or archive.
  2. Domain and email: setup checks the domain points to this server. The email is for certificate notices.
  3. Node name and contact: both appear on XinFin’s public network stats page.
  4. P2P port and APIs: keep the defaults unless you have a reason. eth, net and web3 are on; XDPoS and debug are optional.
  5. Plugin RPCaaS: answer yes only if this node will serve Plugin’s RPCaaS.
  6. Your addresses: the IPv4 addresses or ranges allowed to use the endpoints. Setup offers to add the one you’re connected from.
  7. Admin user, SSH port and root login: a normal user to log in as (setup can create one with a strong password), whether to move SSH to another port, and whether to turn off root login (recommended).
  8. Snapshot, backup password and updates: download a recent copy of the chain instead of syncing from scratch, and choose whether this tool updates itself.

Changing SSH is tested first. If you move the SSH port or turn off root login, setup asks you to log in as your admin user from a second window. The change sticks only once that works, and is undone automatically within 10 minutes if it doesn’t, so you can’t lock yourself out.

The rest runs as a background task with a progress screen: packages, Docker, firewall, certificate, node files, snapshot, first start and a backup. Press q or disconnect and it keeps going; run sudo xdc-rpc to follow it again. If a step fails, setup says why. Fix it, then choose Finish setup: finished steps are checked quickly and skipped.

At the end, setup shows your backup password. Save it: it’s separate from your login password, and a backup can’t be restored without it. When you leave the menu, your endpoints and a test command are printed in the terminal, ready to copy.

6

Test your endpoints

From a computer whose address is on your allowlist. Replace rpc.example.com with your domain.

curl -s -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}' https://rpc.example.com/xdcrpc

It prints the node’s latest block number (in hex). For WSS, with Node.js installed, run npm install -g wscat once, then:

wscat -c wss://rpc.example.com/xdcwss

Paste {"jsonrpc":"2.0","method":"net_version","params":[],"id":1} and expect "50" on Mainnet or "51" on Apothem.

From any other address the connection simply times out: that’s the firewall doing its job. The node answers while it’s still catching up with the network; Status & logs shows how far it has got.

Things to know

Who can connect

The node’s RPC and WebSocket ports listen only on the server itself; nginx serves them over HTTPS. The firewall lets port 443 in only from your allowlist, and nginx checks the allowlist again. Anything that connects without using your domain name, such as scanners trying the IP address, gets nothing back. The node and endpoints use IPv4 only; over IPv6, only SSH is reachable.

Certificates and port 80

The Let’s Encrypt certificate renews itself. Port 80 opens only for the minute or so a renewal takes, then closes again, whether the renewal worked or not.

SSH you can’t lock yourself out of

Every SSH change, such as a new port, root login off or key-only logins, is tested with a real login from a second window and undone automatically if that doesn’t happen. fail2ban blocks addresses that keep failing to log in, for longer each time they come back.

SSH keys, if you want them

Security → SSH keys guides you through making a key on your own computer, testing it, backing it up and turning password logins off. If you ever lose the key, log in through your provider’s web console and run sudo xdc-rpc ssh passwords-on.

Backups and new servers

Your settings, allowlist, certificate, the node’s account and identity, and your admin user’s SSH keys are backed up, encrypted with your backup password, after setup, after changes and daily when anything changed. The newest 10 are kept in ~/XDC-Backups; Backups shows the command to download one to your computer.

To move to a new server, point your domain at it, upload a backup, run the install command and choose Restore from a backup.

Updates

This tool checks for new versions daily and tells you at login. Each download is checked against its published checksum, and if a new version doesn’t apply cleanly the previous one is put back. Ubuntu’s security updates install themselves.

XinFin’s node software never updates by itself. When XinFin publishes a release, you install it from Updates when you’re ready. It’s checked first: if XinFin has changed anything this tool relies on, nothing is installed and your node keeps running as it is. If the new release isn’t working within 10 minutes, the previous one is put back automatically.

Plugin RPCaaS operators

Answer yes to the Plugin question, or turn it on later under Allowlist. Plugin’s gateway address is kept up to date by this tool’s updates, so you never edit it yourself.

The node’s own account

XinFin’s node software creates an account for the node and keeps it unlocked while the node runs. It holds no funds and needs none. Never send funds to it. Node → Node details shows its address.

The node’s own settings

XinFin’s settings file, .env, stays in XinFin’s folder, usually ~/XinFin-Node/mainnet/; Node → Node details shows where. Change settings such as LOG_LEVEL there, then restart the node from the menu. The node name, contact, node type, APIs and RPC switches are looked after by the menu.

Coming from the previous version

If your node was set up with the earlier scripts (install_xdc_rpc_wss.sh and friends), run the install command. It takes over the existing installation and keeps your node, chain data, domain, certificate and allowlist. Cloudflare proxying is no longer used: any Cloudflare ranges on your old allowlist are dropped, so set your DNS record to DNS only.

If something goes wrong

What happenedWhat to do
Setup stopped at TLS certificateCheck the domain’s A record points to this server, that there’s no AAAA record, and that port 80 is open in your provider’s firewall. Then choose Finish setup.
Setup stopped at Chain snapshot with a disk messageAdd disk space, or choose the stream method under Setup & settings → Snapshot method, then Finish setup. An interrupted download continues where it stopped.
Requests to the endpoint time outThe address you’re testing from isn’t on the allowlist. Add it under Allowlist.
The block number is far behindThe node is still catching up. Status & logs shows its progress.
Updates says XinFin’s new release needs a newer xdc-rpcXinFin changed their files in a way this version doesn’t understand yet. Your node keeps running as it is. Update xdc-rpc when a new version is out, then update the node.
You can’t log in after an SSH changeWait 10 minutes: unconfirmed SSH changes undo themselves. Your provider’s web console works too.
Anything elseStatus & logs has the node log and the log of every background task. Where everything is kept, in the same menu, lists every file and folder xdc-rpc uses, and the XDC-RPC-Files folder in your admin user’s home has shortcuts to all of them.
